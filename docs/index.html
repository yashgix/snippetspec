snippetspec

Checks the API calls in documentation code examples against the API's own OpenAPI spec, with no API calls and no model. I ran it on 23 public API docs sites: 1,554 calls checked, and 6 examples on 2 products that disagree with the API, each checked by hand.

github.com/yashgix/snippetspec · MIT

How it got here

  1. 1 · First versionBuilt and tested on one docs site, Supermemory's. It flagged 15 of 15 past docs fixes, but those were found while building it. On a held-out API, Meilisearch, it flagged 53% of untouched examples. It worked, it was noisy, and it confirmed no new bug.
  2. 2 · Built on itA TypeScript version that reads docs pages the way Margin does. It matches the Python verdicts exactly on the test data and on a docs site neither was built on. Four fixes for spec shapes that real sites use: base paths, shared parameters, allOf, and several specs per site.
  3. 3 · Ran it on 23 sites1,554 API calls in public docs, compared with each site's own spec. 6 examples on 2 products send something the API does not take, confirmed against the server code or spec.

How it works

Read MDX pages, find each HTTP call in curl commands, JavaScript fetch and Python requests/httpx code, match it to an operation by method and path template, then check what the example sends. Each call gets one verdict.

MDX pagescode blocks
Calls foundmethod, URL, body
Operation matchmethod and path template
Verdictok, partial, mismatch
  • ok: everything the checker can see agrees with the spec.
  • partial: nothing contradicts the spec, but part of the call could not be read. Not a pass.
  • mismatch: at least one problem, such as an unknown path, a missing or undocumented field, or a wrong type.

Limitations

  • A mismatch means the docs and the spec disagree. It does not say which one is wrong, and no example was run against a live API.
  • The survey read each site's llms-full.txt export, not its MDX source. The export renders some components as Markdown, so a few examples may be missed or read differently.
  • SDK examples are not checked, and they are the largest share of code blocks.
  • A URL that is not a literal (a variable, a relative path) is not seen, so it is neither checked nor counted.
  • When a concrete path exists without the call's method, the checker falls back to a templated path (for example GET /items/search reaches GET /items/{id}). It can hide a wrong-method call.
  • Ledger cases are replayed against today's spec, not the spec of their day.

Technical details

Method, results and data

The 23-site survey

  • Sites: 149 developer-tool docs hosts. 128 serve llms.txt, 49 list an OpenAPI spec under "OpenAPI Specs", 29 of those specs download and parse as JSON, and 23 sites have code examples calling a host in their spec.
  • Pages come from each site's llms-full.txt, split on its Source: lines. Specs were fetched on 2026-11-17. Every call to a spec server host was checked with the same checker as above.
  • Field-level flags were labelled first by DeepSeek (well under one dollar), then every "docs error" label was read by hand against the docs source and, where public, the server code. Findings link to pinned commits.
  • The survey turned up four checker gaps, fixed in both languages: a server URL path in front of spec paths, parameters shared on the path or given by $ref, allOf schemas, and judging a call by the spec it fits best when a site has several (a legacy and a current one). The study results above did not change.

TypeScript version

ts/ reads code examples with remark and remark-mdx using Margin's rules, and its extractor is vendored unchanged under Apache-2.0 with a test that both agree on every Supermemory page. Parity tests compare whole scans with fixtures written by the Python version (148 Supermemory and 216 Meilisearch calls), and both versions agree exactly on Skyvern's 41 MDX pages, which neither was built on. On the survey's rendered llms-full.txt text they differ on 13 sites, because the TypeScript version parses Markdown and MDX properly and the Python one scans lines. Problems can be returned as { path, message, line } records, the shape Margin's ingest validation reports. It is a library and CLI, not a Margin plugin.

What is checked

Matching reads the pinned OpenAPI spec (sha256 checked). Each call is checked for path values, query parameters, body field names, required fields, types, enum values and content type. Exit status is 1 when any call mismatches, so a docs build can gate on it.

What v2 changed and why

The checker passes all 38 v1 acceptance tests. Changes made since v1:

  • A quoting error now skips only the bad command, and unreadable commands are reported, not dropped.
  • A trailing backslash at the end of a block is ignored. This came from reading the first hold-out output.
  • From a later pass over the parser code: explicit Content-Type is checked, fetch is found only in code (not comments or strings), every URL of a curl command is a call, and requests/httpx follow their own body and query rules.

The parser changed after the first hold-out run and again in that later pass. The 24 cases stayed frozen, nothing was tuned to flag more or fewer samples, and the later changes did not move the hold-out counts. Details are in SPEC-v2.md.
