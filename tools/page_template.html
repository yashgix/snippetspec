snippetcheck

Checks the curl, fetch and Python HTTP examples in API documentation against the OpenAPI spec. No API calls, no model.

github.com/yashgix/snippetcheck · MIT · built with Arcturus (Claude Code builders, Codex review), reviewed and verified by hand

The problem

Docs examples drift from the API they describe. In Supermemory's docs history, one commit says the old docs "described a route that has never existed", and a docs PR reports that a namespace-move example sent moveTo in a body the route ignores, "so following the docs permanently deleted the namespace".

The question: from the published spec alone, can every HTTP call in a docs site be checked automatically, and would that have caught the drift bugs the docs team later fixed?

Approach

Read MDX pages, find each HTTP call in curl commands, JavaScript fetch and Python requests/httpx code, match it to an operation by method and path template, then check what the example sends. Each call gets one verdict.

MDX pagescode blocks
Calls foundmethod, URL, body
Operation matchmethod and path template
Verdictok, partial, mismatch

Matching reads the pinned OpenAPI spec (sha256 checked). Each call is checked for path values, query parameters, body field names, required fields, types, enum values and content type. Exit status is 1 when any call mismatches, so a docs build can gate on it.

  • ok: everything the checker can see agrees with the spec.
  • partial: nothing contradicts the spec, but part of the call could not be read. Not a pass.
  • mismatch: at least one problem, such as an unknown path, a missing or undocumented field, or a wrong type.

What v2 changed and why

The build from the written spec (v1) first failed some of the 38 acceptance tests and passes all of them after fixes. After that:

  • A quoting error now skips only the bad command, and unreadable commands are reported, not dropped.
  • A trailing backslash at the end of a block is ignored. This came from reading the first hold-out output.
  • After an independent code review: explicit Content-Type is checked, fetch is found only in code (not comments or strings), every URL of a curl command is a call, and requests/httpx follow their own body and query rules.

The parser changed after the first hold-out run and after review. The 24 cases stayed frozen, nothing was tuned to flag more or fewer samples, and the review changes did not move the hold-out counts. Details are in SPEC-v2.md.

Limitations

  • SDK examples are not checked, and they are the largest share of code blocks.
  • A URL that is not a literal (a variable, a relative path) is not seen, so it is neither checked nor counted.
  • Only the spec is checked. A spec-gap finding means the docs show an endpoint the spec lacks, not that it is dead. A clean result does not mean the example works.
  • When a concrete path exists without the call's method, the checker falls back to a templated path (for example GET /items/search reaches GET /items/{id}). OpenAPI's rule would report a method mismatch. It follows the v1 spec and is left as it is. It can hide a wrong-method call.
  • No real, later-fixed docs bugs were collected for the second API.
  • Ledger cases are replayed against today's spec, not the spec of their day.
